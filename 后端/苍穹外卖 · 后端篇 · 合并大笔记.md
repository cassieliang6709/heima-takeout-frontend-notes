## 一、先建立系统地图

苍穹外卖是一个前后端分离的餐饮系统，包含管理端和用户端。后端是一个 Spring Boot 单体服务，常见请求链路是：

```text
管理端 / 微信小程序
        ↓ HTTP / JSON
Controller（接收请求、参数校验、返回结果）
        ↓
Service（事务、业务规则、组合多个数据操作）
        ↓
Mapper（MyBatis 操作 MySQL）
        ↓
MySQL
```

Redis、OSS、微信接口、WebSocket 和 Nginx 分别承担缓存、文件存储、第三方登录/支付、实时通知和前后端访问入口的职责。

## 二、工程结构与公共能力

### 2.1 三个核心模块

- `sky-common`：常量、异常、上下文、统一返回结果、JSON 和工具类。
- `sky-pojo`：Entity、DTO、VO 等数据载体。
- `sky-server`：启动类、配置、Controller、Service、Mapper 和具体业务。

这样拆分的重点不是“文件夹更整齐”，而是让公共能力、数据模型和业务服务可以分别复用、演进和测试。

### 2.2 DTO、Entity、VO 的边界

- Entity 对应数据库表，适合持久化。
- DTO 表示客户端提交的业务参数，允许一个请求组合多个字段或多个对象。
- VO 表示返回给前端的视图数据，不把数据库内部字段直接暴露出去。

请求进入 Controller 后先从 DTO 读取参数，Service 将 DTO 转为 Entity 或查询条件；查询结果再组装成 VO 返回。这个边界可以避免数据库字段变化直接影响接口。

### 2.3 统一返回与异常处理

成功响应统一携带状态、信息和数据；业务失败使用自定义异常表达可预期错误；全局异常处理器将异常转换成前端能理解的响应，并记录真正的服务端错误。这样客户端不需要理解 Java 堆栈，也不会因为一个异常让接口格式失控。

## 三、Day 1：从环境到第一条请求

### 学习目标

理解前后端分离、开发/测试/生产环境，能启动前端、后端、MySQL、Redis 和 Nginx，并通过接口文档完成一次联调。

### 核心逻辑

1. 导入后端 Maven 父工程和子模块。
2. 创建数据库并加载初始化表结构和数据。
3. 配置数据源、Redis、对象存储等开发环境参数。
4. Nginx 接收页面请求，并将 `/api` 等路径反向代理到后端服务。
5. 登录成功后生成令牌；后续请求携带令牌，由拦截器验证身份。
6. 用 Swagger/Knife4j 或接口工具观察请求参数、响应和错误。

### 必须理解的几个点

- 反向代理隐藏后端真实端口，还能把静态资源和接口统一到同一个入口。
- 登录态不能只依赖前端页面是否打开；服务端必须在每次受保护请求中验证令牌。
- `ThreadLocal` 只适合保存当前请求上下文，必须在请求结束时清理，避免线程复用造成数据串线。

## 四、Day 2：员工与分类管理

### 员工管理的通用 CRUD 模板

员工新增、分页查询、启用禁用和编辑虽然接口不同，但都遵循同一条路径：

```text
产品原型 → DTO/VO → Controller → Service → Mapper → 数据库 → 联调测试
```

新增时校验账号唯一性并保存密码摘要；分页时组合页码、页大小和筛选条件；启用禁用时只更新状态字段；编辑时根据 ID 更新允许修改的字段。对密码等敏感字段要避免明文返回。

### 分页查询的关键

分页不是把全部数据查出来再截取，而是让数据库完成条件过滤和分页。返回结果通常包括总记录数和当前页数据，前端据此绘制分页控件。

### 分类管理

分类既可能关联菜品，也可能关联套餐。因此删除分类前要检查关联数据，否则会产生“页面看似删除、历史数据失去归属”的问题。分类的类型字段决定它服务于哪类业务。

## 五、Day 3：自动填充与菜品管理

### 公共字段自动填充

创建时间、创建人、更新时间、更新人几乎出现在所有业务表中。通过 MyBatis-Plus 的自动填充能力集中处理这些字段，可以避免每个 Service 重复编写，并保证新增和修改的规则一致。

自动填充需要解决两个上下文问题：当前用户是谁，以及当前操作是新增还是修改。前者从请求上下文取得，后者由 ORM 操作类型决定。

### 菜品业务

菜品新增不是单表写入：主表保存名称、价格、分类和图片等信息，口味表保存可选口味。典型流程是先保存菜品主记录，再批量保存口味明细；修改时通常先更新主记录，再删除旧明细并写入新明细。

删除菜品前要检查是否已关联套餐或产生订单，避免破坏业务历史。分页查询则需要把数据库字段组装为前端需要的分类名称、口味列表等 VO。

## 六、Day 4 实战：套餐管理

套餐是菜品组合。新增套餐时既要保存套餐主信息，又要保存套餐与菜品之间的关联关系；修改和删除也必须同时维护主表与关联表。

推荐的实现顺序：

1. 分析产品原型，列出套餐主数据和明细数据。
2. 设计套餐表、套餐菜品关系表及索引。
3. 定义 DTO，允许一次提交套餐基本信息和菜品明细。
4. 在 Service 中开启事务，保证主表与明细表要么一起成功，要么一起回滚。
5. 查询时组装套餐 VO，并在状态变化后同步处理缓存。

## 七、Day 5：Redis 与店铺营业状态

### Redis 为什么放在这里

菜品、套餐和营业状态读取频繁、修改相对少，适合用 Redis 减少 MySQL 查询压力。缓存不是数据库的替代品：MySQL 保存最终事实，Redis 保存可快速重建的副本。

### 店铺营业状态

店铺状态通常只有营业和打烊两种值，适合用一个固定 Redis key 保存。读取接口直接访问 Redis；修改接口更新 Redis。由于这个状态不需要复杂查询，不必为了它单独设计一张业务表。

### 菜品缓存的读写策略

读取：先查缓存，命中则返回；未命中时查数据库、组装结果并写缓存。

修改：先修改数据库，再删除相关缓存。下次读取时重新构建。删除比“直接更新复杂缓存对象”更不容易遗漏关联变化。

## 八、Day 6：微信登录与商品浏览

### HttpClient 与第三方接口

后端调用第三方服务时要明确请求方法、参数、超时、响应解析和失败处理。不要把第三方返回值原样扩散到业务层，应先转换为自己的内部模型。

### 微信登录链路

```text
小程序 code
   ↓
后端请求微信接口换取 openid / session_key
   ↓
根据 openid 查询或创建用户
   ↓
生成用户令牌
   ↓
小程序后续请求携带令牌
```

`session_key` 属于敏感凭证，不应返回给前端或写入日志。用户令牌由自己的服务负责签发和校验。

### 商品浏览

用户端商品浏览通常需要一次返回分类、菜品、套餐及口味等组合数据。Service 负责按业务顺序组装，Controller 只负责接收参数和返回结果。

## 九、Day 7：缓存套餐与购物车

### Spring Cache

Spring Cache 用注解将缓存逻辑从业务代码中抽离：查询方法可缓存结果，修改方法可清理对应缓存。使用时必须明确 key 的组成、缓存边界和失效时机，否则容易出现“管理端已经修改、用户端仍看到旧数据”。

### 购物车

购物车通常与用户身份绑定，适合按用户维度存储。添加商品时需要区分普通菜品、带口味菜品和套餐，判断相同商品与相同口味是否应该合并数量；查看时按用户查询并排序；清空时只删除当前用户的数据。

## 十、Day 8：地址簿、下单与支付

### 地址簿

地址簿属于用户数据。新增、修改、删除和设为默认地址都必须带上当前用户条件，不能只依赖前端传来的用户 ID。设置默认地址时，先取消该用户已有默认地址，再设置目标地址。

### 用户下单

下单是典型事务：

1. 校验购物车非空和商品可售状态。
2. 查询商品最新价格，不能信任购物车缓存中的价格。
3. 查询默认地址并生成订单快照。
4. 写入订单主表和订单明细表。
5. 计算金额并清空购物车。

这些步骤必须在同一个事务中完成，避免只生成订单主表、明细缺失或购物车未清空。

### 微信支付

支付流程涉及商户配置、统一下单、支付回调和订单状态更新。支付回调必须验签、保证幂等，并根据实际支付结果更新订单，不能因为客户端“看起来支付成功”就直接完成订单。

## 十一、Day 9 实战：订单管理

订单管理覆盖历史订单、订单详情、接单、拒单、取消、派送和完成等状态变化。建议先画状态机，再实现接口：不同状态允许的操作不同，状态更新必须带当前状态条件，避免并发请求把订单推进到非法状态。

## 十二、Day 10：定时任务与实时通知

### Spring Task

定时任务适合处理“即使用户不打开页面也必须发生”的事情，例如超时未支付订单关闭、配送中订单超时提醒。任务要尽量短小、可重复执行，并通过状态条件保证重复执行不会造成重复扣减或重复通知。

### WebSocket

WebSocket 用于服务端主动向管理端推送新订单和用户催单。连接建立后需要识别客户端身份；推送失败不能阻塞核心下单流程。消息内容应携带订单 ID、类型和必要摘要，前端收到后再拉取详情。

## 十三、Day 11：运营数据统计

统计接口的难点不在图表，而在指标定义和时间边界。营业额、用户数、订单数和销量排名都要明确：统计哪种订单、是否包含取消订单、日期是否按自然日、开始和结束时间是否包含边界。

典型步骤是：Controller 接收日期范围，Service 生成时间序列，Mapper 使用聚合 SQL 查询，Service 将缺失日期补零，最后组装成 ECharts 需要的横轴和数据数组。

把补零放在 Service 而不是前端，可以保证不同客户端看到一致的统计口径。

## 十四、Day 12：工作台与 Excel 报表

工作台是多个业务指标的组合接口，适合一次查询并组装成专用 VO，避免前端并发调用很多接口。

Apache POI 导出报表的通用流程：

1. 根据日期范围查询营业额、用户、订单和销量数据。
2. 计算合计值、平均值和排名等派生指标。
3. 打开报表模板并填充固定单元格、表格行和图表数据。
4. 设置响应头和文件名，以流的方式返回给浏览器。

导出数据仍然必须遵循和页面统计一致的口径；文件名、编码和流关闭也属于接口正确性的一部分。

## 十五、贯穿全课程的代码检查表

- Controller 是否只做参数接收、校验和返回，不把复杂业务塞进控制层？
- Service 的跨表写操作是否有事务？
- DTO、Entity、VO 是否边界清楚？
- 查询是否有明确的用户/租户/权限条件？
- 更新和删除是否检查当前状态与业务关联？
- 缓存是否有清晰的 key 和失效时机？
- 第三方回调是否验签、幂等并记录必要日志？
- 定时任务和 WebSocket 是否能安全重复执行或失败重试？
- 统计口径是否有明确的日期边界和状态过滤？
- 配置文件中的数据库密码、OSS 密钥、微信密钥是否已脱敏，未提交到公开仓库？
